# Linked semester academics

The semester workspace is shared by web, teacher/admin mobile and student/parent mobile. `GET /api/v1/academics/semester-workspace` provides the role-scoped timeline, current subjects/faculty, today's classes, semester results, backlog details, weighted comparisons and fee ledger. Web and mobile refresh the current class view every minute. Dates and class times use Asia/Kolkata.

Canonical semester start/end dates determine the current semester. Estimated calendars are flagged for confirmation; overlapping terms never silently select a semester. Administrators can edit the complete calendar with revision checks. Calendar changes do not automatically promote students, remove backlogs or move their class enrollment: institutions retain control of promotion policy and class placement through enrollment.

Final results are separate from internal assessment marks. Publish subject marks with an explicit maximum, pass threshold, assessment date and attempt number. Missing marks remain pending. A published passing supplementary attempt supersedes a previous failure. Semester all-clear requires results for every required subject. Graph percentages use earned/maximum published final marks, rather than an unweighted mean. No result is inferred from age or current year.

Teachers can enter results only for allocated subjects and enrolled students. Their scheduled attendance period resolves the subject and semester from the timetable; attendance for a future class has not opened. Parents access only their linked children; students access only themselves. Historical enrollment preserves previous-semester reporting.

Semester fees use explicit semester charges or the existing full-course allocation plan. Annual/unallocated charges remain separate. Payments and balances come from the finance ledger. No synthetic fee splits are generated by the UI.

The persistent-server lifespan runs fee reminders hourly when `EDUNEXA_SEMESTER_REMINDERS_ENABLED=true` (default). It sends one upcoming reminder within seven days, one on the due date, then at most one per overdue week, deduplicated per charge/due date/account. Settled balances stop reminders. The inbox always persists notices; device pushes require the existing configured push adapter and registered device tokens. Local JSON test/development stores do not run this worker. Serverless hosts must invoke the authorized `POST /api/v1/academics/semester-workspace/fee-reminders/run` endpoint from a scheduler because their processes are not persistent. Existing consent-based SMS remains separate.

## Demo records

`tools/seed_linked_academics.py` adds the identifiable `D26-` dataset, reusing existing courses without replacing real accounts or changing their passwords. The dataset has 4 batches, 48 students, 48 parents, 25 faculty and 1 administrator. Subjects, all semester faculty allocations, published weekly timetable templates and canonical slots, attendance, final attempts, assignments, assessments, fees and payments are persisted in SQL. Names, addresses and contacts are synthetic; no external demo notifications are sent by the seed.

```sh
.venv/bin/python tools/seed_linked_academics.py --sql-host 150.241.246.34
.venv/bin/python tools/seed_linked_academics.py --sql-host 150.241.246.34 --apply
```

The apply transaction uses a 300-second query timeout for the bulk insert. All workspace document values are JSON objects, compatible with SQL Server's `ISJSON` check. A run registry prevents duplicate people/accounts; reruns preserve edited records and add only missing demo timetable templates. `mock_logins.txt` is atomically replaced after commit, with mode 0600, and lists created logins and family/subject relationships. The requested demo password is `test@123`. Passwords are hashed in the accounts table, not included in the run registry.

Certificate stationery lives in `app/core/certificate_design.py`, with the bundled Pragathi logo in `assets/pragathi-logo.jpg`. Five designs use A4 portrait, A4 landscape, A5 portrait and US Letter landscape. They share a college seal, issuer signatory, verification QR and the existing cryptographic certificate issuance/verification flow. Previously issued PDFs retain their original bytes.

Deploy backend and dashboard together, include backend/assets, restart the persistent backend, and rebuild/install both Flutter apps. Database inserts alone do not update app binaries or the deployed API code. No schema migration is needed; existing canonical tables and record_extras hold the data.

## Fee-head administration

The course fee cards use the same itemized presentation for every saved course schedule. Custom head names and custom category labels are persisted through the existing fee-head workspace API. The shared fee-head drawer includes the creation form, searchable existing-head table, edit actions, and deletion of unreferenced heads; the API refuses deletion while a head is used. Annual, full-course and explicit semester schedules remain distinct, including when their course/batch/head identifiers overlap. Course selection supplies its actual semester count and filters academic batches to the matching course (legacy shared academic years remain available). Missing itemization is shown honestly as one saved amount, without invented percentage splits.

Android test builds are at `mobile-apps/admin_teachers/build/app/outputs/flutter-apk/app-debug.apk` and `mobile-apps/parent_student/build/app/outputs/flutter-apk/app-debug.apk`. These use the configured test API; deploy the updated API before testing the new semester screens. Firebase/APNs credentials and the push sender adapter are not yet configured; in-app notification records work independently. Device push activation is deferred until the project owner supplies those configurations.
