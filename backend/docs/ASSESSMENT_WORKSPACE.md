# Assessments and semester curricula

The dashboard and both Flutter apps use `/api/v1/academics/assessment-workspace`.

- `GET /options`: course levels, course/branch, eligible batches/sections, semester subjects and teacher profiles. Teachers see allocated classes and subjects.
- `POST /` and `PUT /{code}`: create or edit a draft; publish once. Publishing freezes the recipient roster and instructions. Dates must fall inside the batch and be in the future when publishing.
- `GET /` and `GET /{code}`: scoped lists/details. Published assessments become `completed` dynamically when their scheduled instant passes; no scheduler is required. Mobile and web lists refresh every minute.
- `PUT /{code}/marks`: completed assessments only, revision checked, every mark bounded by the maximum. Whole requests are transactional. Absence and numeric marks are mutually exclusive. Blank marks stay ungraded.

Student accounts see their own published assessments and marks. Parents see linked children, with optional child filtering. Teachers can manage assessments assigned to their teacher profile and may publish only subjects allocated in their teaching classes. Admin role permissions use `exams` and the `assessments` screen.

Publishing and grading create in-app notifications for recipient students and notification-enabled parents. Device pushes use the existing configured push adapter and registered tokens, with `screen=assessments` and `assessment_code`. Push delivery requires the adapter and Firebase/device configuration; an inbox record is available independently.

Images/PDFs use the existing chunked private upload API under `assignment-workspace/files`, with `assessment_upload=true`. The limit is 10 files per assessment and 10 MB per file. MIME signatures are checked, and shared attachment access verifies published audience membership. Files cannot be reused across assessment destinations.

Performance is weighted: total earned marks / total maximum marks for published results. Recorded absences count as zero; ungraded results are excluded. Responses include overall, batch, subject and student breakdowns. Family results also appear in the existing Exam results screen.

## Course and batch plans

`GET/PUT /api/v1/academics/course-curricula/{program_code}` reads/edits semester subject/lab names. Saving requires course edit permission and a matching revision. Every course semester must occur exactly once. Subject counts and lab counts derive from names. Existing subject records remain available for historical allocations even after a course plan is edited.

Plans use the canonical `subjects` and `curriculum_subjects` tables, so they are available to teacher subject offerings and timetable allocation. New dated batches snapshot the course curriculum and get a contiguous dated semester calendar. These initial semester dates divide the batch date range evenly and should be adjusted to the college's actual term calendar. Updating course content affects future batches; existing batch snapshots retain their plan. Assignments can also bind to a curriculum subject and semester; old subjectless assignments remain supported.

New courses receive editable starter drafts. To populate missing semesters for existing courses, run from `backend`:

```sh
.venv/bin/python tools/seed_course_curricula.py
.venv/bin/python tools/seed_course_curricula.py --apply
```

The seed uses the configured storage backend, does not replace existing semester plans, and is safe to rerun. Generated plans are institution-review drafts, not an official university or Intermediate-board syllabus. Credits are starter defaults (3 for theory, 1 for practical); update canonical subject records to institutional requirements. Batch names/codes continue to be generated by the existing server workflow.

Workflow documents persist through the existing SQL `record_extras` storage. No new SQL schema is required. Deploy the backend and dashboard together and rebuild both Flutter applications before enabling this flow.

### Current local/server connection distinction

The dashboard's `EDUNEXA_API_URL` points to the deployed Windows backend. The backend `.env` uses SQL Server `127.0.0.1:1433`, database `Edu Admin`. That address works when the Python process runs on the Windows database server; on a Mac it refers to the Mac instead.

A local `Connection refused (61)` with no listener on port 1433 does not indicate a failed SQL login. Verify the remote `/health` and public course options first. If those respond, keep the working server database settings and run the seed there after copying the updated backend source:

```powershell
Set-Location 'C:\edu portal\backend'
.\.venv\Scripts\python.exe tools\seed_course_curricula.py
.\.venv\Scripts\python.exe tools\seed_course_curricula.py --apply
```

Deploy/restart the updated backend before using the new assessment endpoints. Running the same seed again only fills missing course semesters.

For a Mac development checkout whose `.env` retains the Windows server's local SQL address, the seed supports a temporary host override:

```sh
.venv/bin/python tools/seed_course_curricula.py --sql-host 150.241.246.34
.venv/bin/python tools/seed_course_curricula.py --sql-host 150.241.246.34 --apply
```

This uses the existing configured database name/login and does not edit `.env`. The remote SQL target was checked against the live API's public course codes before use. To run a local backend against that server, set `EDUNEXA_MSSQL_HOST=150.241.246.34` in the local process environment; the Windows backend should retain its own working settings.
